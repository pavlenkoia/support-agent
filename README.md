# Агент поддержки

Сервис поддержки на FastAPI с PostgreSQL, Telegram/VK-воркерами, read-only Viewer и LLM-ответами. В production режим `jev_selected_fact`: Jev выбирает один факт из **структурированного JSON-артефакта знаний**, отвечающая LLM получает только выбранный факт и контекст диалога. Wiki и Markdown не передаются провайдерам.

## Актуальная архитектура знаний

```text
Авторская Wiki с `runtime_facts`
        ↓
валидация и candidate-сборка
        ↓
knowledge-base.v1.json
        ↓ атомарная публикация
/data/profile/kb/knowledge-base.v1.json
        ↓
Jev Choice по опубликованным фактам → один выбранный факт → отвечающая LLM
```

### Runtime KB

Единственный model-facing файл:

```text
/data/profile/kb/knowledge-base.v1.json
```

Его схема:

```json
{
  "schema_version": 1,
  "facts": [
    {
      "id": "jump.schedule.weekends",
      "text": "Прыжки обычно проходят по субботам и воскресеньям.",
      "conditions": ["Проведение зависит от погоды."],
      "source_refs": ["schedule:01"]
    }
  ]
}
```

В KB допустимы только явные курируемые факты: семантический `id`, клиентский текст, условия применимости и логические ссылки на источник. В runtime запрещены Markdown, YAML/frontmatter, пути файлов, raw-документы, журналы, редакторские инструкции, навигация и автоматически извлечённые из Wiki фразы.

### Единственный authoring source

Каноническими являются явные `runtime_facts` в YAML-frontmatter тематических Wiki-страниц под `deploy/profile-source/kb/`. Компилятор читает только эти blocks и собирает из всех страниц один `kb/knowledge-base.v1.json`; отдельного редактируемого реестра facts нет.

`scripts/build_runtime_profile.py` не выводит факты из Markdown regex-разбором.

## Работа support-governor

Governor работает через ограниченный tool `support_kb_bundle` и не получает доступа к коду приложения, Docker, Git, промптам или секретам.

Поддерживаемый безопасный цикл изменения facts:

1. `read` — Governor читает актуальную тематическую Wiki-страницу вместе с её `runtime_facts` и SHA-256.
2. Governor меняет обычный текст и соответствующие `runtime_facts` в одной полной странице.
3. `apply` передаёт страницу, `reason`, `expected_sha256`; сначала допускается `dry_run: true`.
4. Publisher валидирует Wiki, компилирует facts из её же snapshot и атомарно заменяет runtime KB.
5. Следующий запрос воркера читает новый JSON без перезапуска контейнеров.

`expected_sha256` защищает от перезаписи более свежей правки. При ошибке валидации или сборки текущий production KB остаётся прежним. Receipt и backup создаются publisher-ом; rollback возможен заменой KB из его backup.

Обычная авторская Wiki — единственный источник facts и provenance-слой: никакого отдельного редактируемого JSON-реестра нет.

## Прежний контракт one-call ответа (неактивный в production)

В режиме `simple_full_corpus_natural` один provider call получает текущий буквальный вопрос, ограниченную историю диалога и полный compact runtime KB. Промежуточный semantic selector не используется: прошлые эксперименты показывали, что он чаще теряет нужную часть многосоставного вопроса, чем устраняет лишние детали.

При выборе старого режима `SIMPLE_ANSWER_PROMPT.md` требует:

- выделить все самостоятельные части вопроса и покрыть каждую подтверждёнными facts;
- не заменять одну часть тематически близким, но нерелевантным фактом;
- считать короткую разговорную формулировку и отсутствие вопросительного знака возможным уточняющим запросом, а не признаком социального сообщения;
- использовать историю только для понимания предмета уточнения, но не повторять ранее сообщённые факты без нового запроса;
- отвечать ровно `Пожалуйста!` только на явное завершение разговора с благодарностью или прощанием без запроса, уточнения, просьбы или выбора;
- не добавлять неподтверждённые сведения, внутренние объяснения или необязательные призывы к следующему действию.

Историческое требование этого режима — покрывать все самостоятельные части вопроса. В действующем Jev-режиме сознательно выбирается один факт по главному вопросу; не применять к нему правило полного покрытия из этого раздела.

Для старого one-call пути нужны `SIMPLE_ANSWER_PROMPT.md`, `profile.yaml` и generated `kb/knowledge-base.v1.json`. Действующий Jev-путь использует `JEV_ANSWER_PROMPT.md`, `JEV_DIALOGUE_PROMPT.md`, `profile.yaml` и тот же generated KB.

## Режим Jev

В production задан `ANSWER_ENGINE_MODE=jev_selected_fact`; значение по умолчанию в коде — `simple_full_corpus_natural` и не отражает действующий режим. Jev-ключ `JEV_API_KEY` хранится вне репозитория в runtime env; `JEV_MODEL` по умолчанию — `typesafe/jev-1.13`. Jev System One сначала выбирает тип реплики с учётом истории и области поддержки; для содержательного вопроса вторым `Choice` выбирает ровно один предметный факт опубликованного KB либо `no_answer`. Выбор главного вопроса в составном сообщении не означает покрытия всех частей. Отвечающая модель получает только выбранный факт, условия, вопрос и историю; `no_answer` использует текст из `profile.yaml` без вызова отвечающей модели. Диалоговые правила об уточнении клиента не публикуются как выбираемые факты: при отсутствии ответа используется фолбэк, а не встречный вопрос. Для социальной реплики Jev учитывает историю, но отвечающая модель получает только текущую реплику и может вернуть JSON или короткий обычный текст из `content`; `reasoning_content` клиенту не передаётся. `DIRECT_LLM_THINK_ENABLED=false` по умолчанию: `true` включает размышление для всех вызовов отвечающей модели (предметных и социальных), `false` выключает; Jev и суммаризатор не меняются. Переменная читается при запуске сервиса — для смены режима нужен перезапуск использующих её контейнеров. Предметный ответ принимает JSON с `response_text` или ограниченный обычный текст из `content` при одном выбранном факте; некорректный JSON, пустой `content` и `reasoning_content` не выдаются клиенту. Оффтопик и флуд остаются отдельными диалоговыми типами без KB. Ошибки выбора/ответа переходят в `retry_pending`, а не маскируются под отсутствие факта.

Выбранный ID подтверждает происхождение факта, но не доказывает семантическую корректность клиентской фразы. Для разбора инцидентов событие `jev_fact_selected` сохраняет точный текст факта, условия, ссылки на источники, SHA-256 KB и `trace_id` обращения; оно записывается и при ошибке отвечающей модели. События `response_strategy_selected` и `inbound_processed` содержат тип реплики, ID факта либо стадию ошибки и итоговый маршрут. Вероятности Jev не сохраняются.

## Компоненты

- `app/` — FastAPI и логика агента;
- `viewer-web/` — React/Tailwind Viewer VK-диалогов;
- `deploy/` — профиль, deploy-материалы и runtime-монтирование;
- `scripts/` — сборка профиля и эксплуатационные скрипты;
- `tests/` — тесты контрактов и runtime-поведения.

```bash
curl http://127.0.0.1:8000/health
```

## Production release

Перед выпуском профиль собирают из canonical source, проверяют candidate и точное соответствие внешнему runtime-профилю. Затем выполняют:

```bash
python3 scripts/release.py
```

Не выкатывайте отдельные Compose-сервисы вместо проверенной процедуры релиза. Runtime env и секреты находятся вне репозитория.
