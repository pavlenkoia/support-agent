# Спецификация: объединение входящих сообщений в один пользовательский ход

**Статус:** согласовано для реализации
**Проект:** `/home/tian/support-agent`
**Цель:** не отвечать отдельно на каждую короткую реплику клиента, отправленную в догонку, и не допускать одновременных или устаревших ответов в одном диалоге.

## 1. Область изменения

Изменение выполняется в общем входящем контуре между транспортными адаптерами и `RoutingService.handle_inbound()`.

Механизм должен быть единым для всех текущих и будущих каналов. Telegram, VK и последующие каналы не должны реализовывать собственную бизнес-логику объединения сообщений.

Промпты, KB, маршрутизация вопросов и логика формирования клиентского текста не изменяются.

Вложения не входят в эту спецификацию.

## 2. Термины

- **Исходное сообщение** — одно сообщение, полученное от канала, с внешним идентификатором и временем получения.
- **Пакет** — последовательность исходных сообщений одного диалога, ожидающая обработки.
- **Объединённый ход** — один `InboundMessage`, созданный из текстов пакета и переданный в `RoutingService`.
- **Ревизия пакета** — монотонно растущая версия пакета; увеличивается при каждом новом исходном сообщении.
- **Устаревшая генерация** — генерация, запущенная для более ранней ревизии пакета.

## 3. Ключ диалога

Очередь изолируется по ключу:

```text
(channel, external_chat_id)
```

Сообщения разных диалогов никогда не объединяются и не блокируют друг друга.

## 4. Временные параметры

- Окно тишины после последнего исходного сообщения: **5 секунд**.
- Максимальное ожидание от первого исходного сообщения пакета: **15 секунд**.
- Пакет готов к обработке при наступлении первого из условий:
  - прошло 5 секунд без нового сообщения;
  - прошло 15 секунд с первого сообщения пакета.

Параметры должны находиться в общей конфигурации приложения, но значения по умолчанию фиксируются этой спецификацией:

```text
INBOUND_COALESCE_QUIET_SECONDS=5
INBOUND_COALESCE_MAX_WAIT_SECONDS=15
```

## 5. Приём сообщения

Для каждого поддержанного текстового сообщения транспортный адаптер обязан:

1. проверить обязательные идентификаторы и выполнить существующую авторизацию канала;
2. построить канонический `InboundMessage`;
3. выполнить существующую защиту от повторной доставки по внешнему идентификатору;
4. сохранить исходное событие в `transport_events` для аудита;
5. передать сообщение в общую входящую очередь;
6. сразу вернуть управление polling/webhook-контуру, не ожидая LLM и отправки ответа.

До закрытия пакета `RoutingService.handle_inbound()` не вызывается, а запись в `messages` не создаётся.

## 6. Формирование объединённого хода

Тексты исходных сообщений объединяются:

- в порядке фактического получения;
- через один перевод строки;
- без перефразирования, классификации и анализа содержания;
- без удаления отдельных непустых реплик.

Пример:

```text
Здравствуйте
Сколько стоит прыжок с самолёта?
```

В таблице `messages` сохраняется одна пользовательская запись с объединённым текстом.

Исходные сообщения, их внешние ID, исходные timestamps и raw payload остаются отдельными записями в `transport_events`.

## 7. Сериализация по диалогу

Для одного ключа диалога разрешена только одна активная генерация.

Другие диалоги должны обрабатываться независимо и параллельно.

Вызов `RoutingService.handle_inbound()` и отправка результата выполняются вне polling/webhook-потока, чтобы транспорт продолжал принимать новые сообщения во время генерации.

Синхронный вызов LLM может физически продолжаться после отмены. В этой спецификации отмена означает обязательное признание результата устаревшим и запрет его отправки клиенту.

## 8. Новое сообщение во время генерации

Если новое исходное сообщение пришло, пока ответ для этого диалога генерируется:

1. сообщение добавляется к текущему пакету;
2. ревизия пакета увеличивается;
3. текущая генерация помечается устаревшей;
4. её результат запрещено отправлять и сохранять как исходящий ответ;
5. после окна тишины либо достижения максимального срока запускается новая генерация;
6. новая генерация получает весь объединённый текст пакета, включая ранее обработанные части.

Перед любой внешней отправкой выполняется атомарная проверка:

```text
generation_revision == current_package_revision
```

Если равенства нет, отправка запрещена.

## 9. Завершение пакета

Пакет считается завершённым только после успешной отправки актуального ответа либо после явного подавления бот-ответа человеком-администратором.

После успешной отправки:

- сохраняется один исходящий assistant message;
- исходные `transport_events` пакета помечаются обработанными;
- состояние пакета удаляется из памяти.

При ошибке провайдера или транспорта применяются существующие правила `retry_pending` и доставки. Повтор не должен создавать второй пользовательский ход или второй ответ на ту же ревизию.

## 10. Ответ человека-администратора

При обнаружении ответа человека-администратора в диалоге общий механизм обязан:

1. активировать существующий human override;
2. отменить ожидающий пакет;
3. пометить активную генерацию устаревшей;
4. запретить отправку результата бота;
5. не создавать бот-ответ на отменённый пакет.

Проверка human override выполняется повторно непосредственно перед внешней отправкой.

Этот контракт должен использоваться всеми каналами, которые умеют обнаруживать ответ администратора. Канальная детекция остаётся в транспортном адаптере; отмена пакета выполняется общей очередью.

## 11. Хранение и перезапуск

Состояние пакетов и активных генераций хранится только в памяти процесса.

При перезапуске worker/container допускается:

- потеря незапущенного пакета;
- отсутствие автоматического ответа на сообщения этого пакета.

Сохранённые `transport_events` остаются для аудита, но автоматически не переигрываются.

Это согласованное ограничение. Персистентная очередь и восстановление после перезапуска не входят в эту спецификацию.

## 12. Размещение в коде

Предполагаемые изменения:

- создать общий сервис очереди: `app/services/inbound_queue.py`;
- добавить настройки в `app/core/config.py`;
- подключить общий сервис в `app/services/telegram_gateway.py`;
- подключить общий сервис в `app/services/vk_gateway.py`;
- привести Telegram к сохранению raw transport events и dedupe-контракту;
- уведомлять общий сервис об admin override из канальных адаптеров;
- при необходимости адаптировать worker loops в `app/workers/main.py` и `app/workers/vk_main.py`, чтобы очередь и генерации обслуживались независимо от polling;
- не переносить бизнес-логику в канальные gateway-классы.

Точная файловая декомпозиция может уточняться при реализации, но единый channel-independent сервис и расположение перед `RoutingService.handle_inbound()` являются обязательными.

## 13. Наблюдаемость

Для каждого пакета необходимы внутренние события/метрики без клиентского текста:

- `inbound_batch_opened`;
- `inbound_message_coalesced`;
- `inbound_batch_flushed`;
- `generation_superseded`;
- `inbound_batch_cancelled_by_human`;
- `inbound_batch_delivered`.

Минимальные поля:

```text
channel
external_chat_id
batch_id
revision
source_event_count
opened_at
last_message_at
flush_reason: quiet_window|max_wait
```

Логи и трассы не должны содержать секреты или raw payload целиком.

## 14. Требования к тестированию

### Модульные тесты общей очереди

1. Одно сообщение обрабатывается после 5 секунд тишины.
2. Второе сообщение в пределах 5 секунд продлевает окно тишины.
3. Пакет запускается не позднее 15 секунд от первого сообщения.
4. Тексты объединяются через перевод строки в порядке получения.
5. Разные диалоги не объединяются и не блокируют друг друга.
6. В одном диалоге не работают две актуальные генерации одновременно.
7. Новое сообщение во время генерации делает старый результат неотправляемым.
8. Новая генерация получает полный объединённый текст.
9. Human override отменяет пакет и запрещает отправку.
10. После успешной отправки состояние пакета очищается.
11. Повторный transport event не добавляется в пакет второй раз.
12. Перезапуск не требует восстановления in-memory пакета.

### Интеграционные тесты каналов

- Telegram и VK передают сообщения в один и тот же контракт общей очереди.
- Polling продолжает принимать сообщения, пока другой ответ генерируется.
- Raw transport events сохраняются отдельно.
- В `messages` создаётся один объединённый user message и один assistant message.
- Проверка override непосредственно перед отправкой подавляет устаревший ответ.

### Обязательный регрессионный сценарий обращения 613

Ввод:

```text
Здравствуйте
Сколько стоит прыжок с самолёта?
```

Ожидание: один пользовательский ход и один ответ.

Следующий ввод:

```text
Муж хочет прыгнуть с парашютом😁
Хочу ему сделать подарок
```

Ожидание: один пользовательский ход и один ответ по полному смыслу обеих реплик.

Запрещено отправлять отдельный ответ на каждую строку.

## 15. Критерии приёмки

Изменение принято только если одновременно выполнены условия:

- окно тишины равно 5 секундам;
- максимальное ожидание равно 15 секундам;
- подряд отправленные сообщения одного диалога становятся одним user message;
- устаревший результат никогда не отправляется;
- в одном диалоге нет параллельных актуальных ответов;
- разные диалоги обрабатываются независимо;
- human override отменяет буфер и генерацию;
- Telegram и VK используют один общий механизм;
- raw transport events сохраняются отдельно;
- существующая логика промптов, KB и ответов не изменена;
- модульные и интеграционные тесты проходят;
- сценарий обращения 613 подтверждён буквальным runtime replay без отправки в клиентский канал.

## 16. Вне области работ

- анализ смысла частей сообщения до объединения;
- списки фраз и keyword-routing;
- изменения `SYSTEM_PROMPT.md` и `KB_AGENT_PROMPT.md`;
- изменение KB;
- обработка вложений;
- персистентная очередь;
- восстановление незапущенных пакетов после перезапуска;
- повторная отправка исторических transport events;
- изменение бизнес-правил human override.
