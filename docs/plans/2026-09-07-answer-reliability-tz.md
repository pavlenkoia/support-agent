# ТЗ: надёжность ответов support-agent

> Для Hermes: перед реализацией загрузить `subagent-driven-development`, `test-driven-development`, `support-agent-development-workflow`, `support-agent-finalizer-contract` и `implementation-verification-discipline`. Выполнять только один явно выбранный этап за сессию. Этот документ описывает всю программу, но не разрешает самостоятельно переходить между этапами или менять production.

**Цель:** агент даёт естественный ответ на фактический вопрос только в пределах подтверждённых Wiki/инструментами сведений; не теряет ограничения при финализации, исполняет заявленную последовательность инструментов и различает отсутствие знания, ошибку протокола и технический сбой.

**Архитектура:** один ограниченный LLM-управляемый ход, исполняемые типизированные инструменты, компактный пакет подтверждённых сведений и одна общая граница формирования клиентского текста. Прикладной код обеспечивает структуру, допустимые состояния, границы данных и доставки, но не принимает бизнес-решения по ключевым словам.

**Стек:** Python, существующие сервисы приложения, SQLAlchemy/PostgreSQL, pytest, OpenAI-compatible клиент, Docker Compose, Telegram/VK.

**Статус:** ТЗ для последующей реализации. В этой сессии сохранён только документ. Исправления не выполнены, production-релиз не разрешён.

## 2. Подтверждённые основания

### F1 — неподтверждённый отправленный ответ

Case 934, workflow event 6398, 6 сентября: клиент спросил о конкретной вчерашней съёмке самостоятельного прыжка. Wiki вернула `ready` со сведениями о примерах видео в ленте VK и видеосъёмке тандема. Ответ добавил, что инструкторы публикуют съёмку именно там, и предложил получить ссылку через администратора. Эти связи не следовали из сохранённых grounded facts. Доставка доказана outbound 456 / VK 34579 / callback 1278; исходное событие 1277 / VK 34578.

Все пять LLM-вызовов успешны. Без сохранённого полного пакета, в частности answer_basis, нельзя окончательно разделить вклад extraction и finalizer. Исправлять границу evidence → ответ, а не приписывать всё последней модели без доказательства.

### F2 — неисполнимая последовательность инструментов

`direct_llm.py:75,91–92` разрешает два последовательных инструмента. `agent_tool_loop.py:52–69` после Wiki возвращает KB-пакет; `routing.py:157–165` вызывает отдельный `respond`. После календаря `direct_llm.py:170–180` требует финальный ответ без инструментов; `agent_tool_loop.py:109–110` отвергает следующий tool request. Fake-проверка воспроизвела calendar → wiki request → retry_pending, wiki_calls=0.

### F3 — небезопасная граница результата

`direct_llm.py:397–440`: JSON-массив и `confidence:null` вызывают исключения при нормализации после блока перехвата ошибок. Неизвестный route превращается в cannot_answer с сохранённым текстом. `direct_llm.py:443–446` обрезает ответ до 1000 символов, включая середину слова; завершающее ограничение исчезает при сохранении route=answer. Проверить также общий PolicyService: исправление не должно оставлять второй срез ниже по цепочке.

### F4 — неполная/искажённая наблюдаемость

`routing.py:192–215`: причина подменяется названием route, confidence фиксируется как 1.0, attempts=0 считается как 1; точный запрос инструмента и пакет финализации не сохраняются. Документация overview описывает native continuation для Wiki, чего текущий код не делает.

История 517 inbound_processed / 456 retry_pending не является процентом ошибок по уникальным клиентским сообщениям. Она включает повторы, операторский трафик и разные релизы/провайдеры. Старые received-события не разрешено переотправлять или массово исправлять в рамках этого ТЗ.

## 4. Обязательные целевые контракты

### C1. Один ход и один владелец клиентского текста

Вход: текущий вопрос либо упорядоченный объединённый ход и ограниченный диалог действующей сессии.

LLM выбирает зарегистрированные инструменты по смыслу. Исполнитель поддерживает 0–2 последовательных вызова, без параллелизма; в данном объёме каждый из wiki_lookup/calendar_lookup — не более одного раза. Оба порядка должны реально работать. Повтор/третий вызов — явное нарушение бюджета с внутренней причиной и безопасным техническим исходом, не cannot_answer и не догадка. Внутренние повторные HTTP-попытки не считаются отдельным tool action.

Последовательность выбора действий не создаёт второй классификатор: использовать существующую модельную границу, не добавлять новую LLM-роль. Решение «завершить сбор» не содержит самостоятельного клиентского черновика. Клиентский текст создаёт одна общая финализация после сборки пакета — для Wiki, календаря, их сочетания и допустимого социального ответа. Не генерировать текст на одной ветке с последующим ненужным переписыванием на другой.

Чистая социальная реплика не требует Wiki. Содержательный бизнес-ответ не может опираться на социальный route для обхода evidence. Диалог помогает понять выбранный предмет, но не доказывает факт. Календарь не доказывает расписание бизнеса.

### C2. Подтверждённые сведения и покрытие вопроса

Не менять файловую схему Wiki. Сформировать внутренний версионированный типизированный пакет на существующей границе extraction/tool → finalization:

- исходный вопрос/объединённый ход и выбранное контекстное ограничение;
- состояние получения данных отдельно от покрытия вопроса;
- факты с устойчивыми локальными ID, текстом, source refs, условиями и модальностью, если они есть в источнике;
- явно подтверждённая часть вопроса и непокрытые части;
- конфликты, неразрешённые ограничения и отсутствие прямого ответа;
- календарные факты отдельно от бизнес-фактов;
- allowlisted policy evidence с источником, когда она применима.

Нельзя дополнять отсутствующие условия/модальность из модели. Связь факта с source_ref валидируется структурно; это не считается доказательством семантической верности извлечения. Отдельный LLM-вызов для проверки не добавлять: формирование пакета встроить в существующий этап extraction.

`answer_basis` при сохранении остаётся кандидатной формулировкой/сводкой, а не независимым источником знания. Не использовать её для оправдания утверждения, которого нет в фактах. Отсутствие упоминания не превращается в отрицательный факт. Тематическая близость не равна прямому покрытию. Слова «обычно/возможно/рекомендуется» не усиливаются до безусловного результата.

На неполный вопрос допустим ответ на подтверждённую часть с честным обозначением границы. Не требовать всеобщего отказа из-за одного непокрытого подпункта. Для ясного, но неизвестного вопроса — естественный cannot_answer; clarification только если неоднозначность действительно устранима ответом клиента. Не обещать действия/обратную связь/контакт без profile-backed evidence.

### C3. Состояния и техническая безопасность

- found/ready: данные получены; отдельно проверяется покрытие текущего вопроса.
- not_found: успешное получение семантического результата без прямого знания; не retry_pending.
- unavailable: provider/transport/parse/schema failure; не «в Wiki нет сведений».
- invalid tool / budget violation / invalid final output: технические причины, отдельные reason codes, без клиентского текста.
- retry_pending: отсутствуют assistant message и outbound send; работает существующее durable recovery. Не превращать в waiting_human автоматически и не делать вечный быстрый цикл в рамках одного запроса.

Текущие retry/backoff не переписывать в данном ТЗ. Повторяемая логическая ошибка, найденная при приёмке, блокирует кандидат, а не считается успешной устойчивостью благодаря повторам.

### C4. Выходной контракт

Одна общая валидация применяется ко всем результатам модельных границ до маршрутизации, форматирования и сохранения:

- верхний уровень — объект; route — точное значение поддерживаемого enum;
- response_text — строка, непустая для клиентского исхода; объект/список не преобразуется через str в ответ;
- confidence не управляет фактической истинностью. Отсутствующий/null допускается как неизвестный (`None`) и не ломает полезный ответ. Конечное число 0..1 допустимо; bool, нечисловая строка, NaN/Infinity и значение вне диапазона — нарушение схемы;
- неизвестный route не переименовывается в cannot_answer;
- технический результат всегда textless;
- причина сохраняется отдельно от outcome, не подменяется именем route;
- ожидаемые ошибки разбора/валидации не выходят необработанными наружу; неожиданные исключения не маскируются под бизнес-отказ.

Не добавлять зависимость от provider-native JSON Schema: приложение самостоятельно валидирует ответ совместимого клиента.

Убрать семантически опасный срез `[:1000]` по всей реальной выходной цепочке. Ответ допустимой для канала длины сохраняется целиком, включая завершающие ограничения и переносы строк. Перед реализацией установить фактические ограничения действующих адаптеров и форматирования. При превышении проверенного предела — явное output_too_long с пустой отправкой, без молчаливого обрезания; автоматический LLM-переписыватель/многочастная отправка не входят в этап 1. Этот редкий failure path не должен подменять нормальное прохождение ответа длиной более 1000 символов, если он укладывается в предел канала.

Сохранить однократное приветствие и существующие защиты от внутренних технических конвертов; не вводить словари бизнес-фраз.

### C5. Воспроизводимость и наблюдаемость

В workflow/probe-представлении сохранять версию контракта, упорядоченные действия с call IDs, валидированный tool request, минимальный фактический пакет финализации (включая использованный candidate basis), outcome и точный reason, модель/провайдер/попытки/длительности, связь с исходным ходом и итоговой отправкой.

Не хранить chain-of-thought, ключи, полный raw HTTP, все страницы Wiki или безразмерные контексты. Для минимального пакета задать размерный предел; при его превышении не терять молча audit-доказательство. До записи поля проверить совместимость Viewer/governor и использовать существующий JSON workflow payload, без обязательной миграции.

Ноль попыток остаётся нулём; отсутствующая метрика — неизвестной. Metadata-only строки не увеличивают счётчик реальных модельных вызовов. kb_status относится к Wiki и не обязан становиться ready из-за календаря; добавить отдельный evidence/tool status вместо переименования смысла старого поля.

**Файлы:** `app/services/kb_agent.py`, граница пакета в `agent_tool_loop.py`/`routing.py`, `app/services/direct_llm.py`; тесты `tests/test_kb_agent.py`, `tests/test_kb_agent_evidence_coherence.py`, `tests/test_direct_llm_grounding_boundary.py`; новый `tests/test_answer_evidence_contract.py`.

1. По сохранённым пакетам этапа 2 отделить extraction-ошибку от finalizer-ошибки; не предполагать единственного виновника.
2. Зафиксировать JSON/schema внутреннего пакета C2, размерные пределы и поля для missing/conflict без изменения Wiki на диске.
3. Показать точный prompt diff, перечень сохранённых русских положений и получить подтверждение до записи. Никаких бизнес-кейсов внутри инструкций.
4. RED-тесты: тема совпадает, прямого ответа нет; отрицательный факт vs отсутствие упоминания; частичное покрытие; противоречие basis/facts; условия/модальность; сохранение выбранного предмета; техническая недоступность vs not_found.
5. Реализовать пакет на существующем extraction, его структурную валидацию и использование общим финализатором. Не добавлять шестой проверяющий LLM-вызов.
6. Провести literal no-send replay набора раздела 6. Проверять каждый фактический тезис по конкретному source/evidence, а не по route/confidence.
7. Полный suite, независимое ревью scope/evidence, scoped commit; зафиксировать буквальный результат и границы проверки.

**Приёмка:** отсутствуют неподтверждённые утверждения и потерянные существенные условия в утверждённом корпусе. Если literal replay провалился, этап не принят: сохранить неудачный кандидат и STOP, не наращивать ситуативные prompt-правила в той же сессии.

### Этап 5 — интегральная кандидатная приёмка (отдельная сессия)

**Цель:** доказать совместимость исправлений с диалогом и доставкой, подготовить решение о релизе.

1. Собрать изолированный кандидат из конкретного commit. Проверить актуальную production parity по разрешённым параметрам, неизменность исходной Wiki и no-send гарантии.
2. Полный suite в каноническом Docker-окружении и интеграционные сценарии с PostgreSQL.
3. Прогнать раздел 6, включая реальные последовательности и fake-транспорт для обоих каналов.
4. Для двух отмеченных в ревью предполагаемых transport test gaps сначала проверить существующие тесты. Только если покрытия действительно нет, добавить targeted fake-interleaving тесты reconciliation и retry send boundary; не объявлять баг до RED и не переписывать транспорт автоматически.
5. Подготовить manifest commit/profile/model, доказательства, список открытых дефектов и вердикт «кандидат готов/не готов».

**STOP:** production deploy в программу не входит. После принятия кандидата нужен отдельный запрос Игоря на релиз с rollout/rollback и проверкой всех исполняющих контейнеров. Нельзя говорить «исправлено в production» по одному кандидатному прогону.

## 6. Обязательный корпус и критерии приёмки

Создать версионированный manifest сценариев. Разделять буквальный исторический replay и обезличенные synthetic/fault fixtures. Исторический ответ оператора — контекст расследования, не автоматический источник бизнес-факта для модели.

1. **Case 934:** буквальный вопрос о конкретной съёмке. Не утверждать, что это видео находится в ленте примеров; не придумывать публикацию инструкторов или помощь администратора. Если знания по-прежнему отсутствуют — естественный честный ответ без выдуманной процедуры.
2. **Case 905:** ordered user turns из сохранённого evidence-файла. Отдельный frozen-evidence тест старого «не указано» → не превращать в «запрещено»; отдельно replay на текущей Wiki, с учётом её легитимных последующих изменений. Не требовать от нового корпуса старого ошибочного факта.
3. **Case 930:** исходное сообщение и добавленный возраст одним объединённым ходом; сохранить оба требования, не потерять уточнение. Оценивать по действующей Wiki, не кодировать возраст в core/prompts. Последовательный replay и grouped replay — отдельные проверки.
4. **Комбинированный вопрос с бизнес- и календарным фактом:** оба порядка tool calls, точные календарные данные, отсутствие выведенного из календаря бизнес-расписания.
5. **Чистая социальная реплика:** без Wiki/бизнес-фактов, корректный ответ и однократное приветствие.
6. **Ясный неизвестный вопрос:** not_found → естественный cannot_answer, без ложного уточнения и без технического retry.
7. **Действительно неоднозначный запрос:** уточнение только по смыслам из текущего диалога, без придуманных вариантов.
8. **Смешанное покрытие:** подтверждённая часть отвечена, неизвестная не достроена; сохранены существенные условия.
9. **Технические/структурные отказы:** provider timeout, malformed JSON, invalid tools, пустой финальный текст; ноль клиентских сообщений, точная причина, durable retry по существующему контракту.
10. **Длина/формат:** допустимый длинный ответ целиком; запредельный не обрезается; переносы не теряют структуру; отсутствие служебного конверта.
11. **Новое входящее и ручной ответ во время генерации:** fake sender подтверждает подавление устаревшего результата; один актуальный итог, отсутствие дублей; оба канала.

Каждый детерминированный случай — RED до исправления соответствующего дефекта, GREEN после. Каждый семантический live-сценарий — три независимых прогона с теми же входами/профилем/моделью; записывать все попытки, не выбирать лучший. Это приёмочная выборка, не статистическая гарантия отсутствия галлюцинаций. Provider failure — прерванный прогон, не семантический pass; повтор исходного хода без дублирования inbound. Технические прерывания и стоимость учитывать отдельно.

Артефакт каждого replay: literal ordered input, фактические инструменты, evidence packet, точный output, route/reason, trace ошибок/попыток, длительность и токены, отсутствие внешней отправки, идентичность контейнера/commit/profile/model. Новая скорость не компенсирует ухудшение фактической точности. Не устанавливать произвольный SLA без baseline; сравнить задержки и стоимость до/после на одном корпусе.
